# 后端用例与功能边界决策记录

> 状态：讨论中
>
> 最后更新：2026-07-28
>
> 本文持续记录本轮 grilling 中已经确认的决策。未标记为“已确认”的内容不得视为需求。

## 1. 产品用例边界

后端收敛为两个独立 Agent 工作流和一个共享人才数据产品：

1. 简历评估 Agent；
2. 人才知识 Agent；
3. 人才知识库，作为两条 Agent 工作流共享的数据与展示底座，本身不是第三条评估 Agent。

“按研究关键词发现一批未知人物”的人才发现用例尚未实现，本阶段明确不做。

## 2. 已确认决策

### 2.1 简历评估

- 简历评估输出能力结构、评分和推荐 Track，但评分不自动决定通过、不通过或人才分档。
- 不论候选人处于高年级还是低年级，简历中的论文都检查投递/发表状态和作者顺序。
- 论文状态不能依赖固定关键词匹配。AI 应结合论文条目和简历上下文进行语义判断，再输出受控的结构化状态。
- 每条 AI 状态判断应保留原文证据、判断理由和置信度。
- 简历明确标注的状态属于候选人自述，不能伪装成外部核验事实。
- 简历未标注状态但提供期刊或会议信息时，系统尝试从外部来源查找；找到对应论文后可按已发表处理。
- 简历未标注状态且外部来源也查不到时，统一标记为“待核查”。
- 草稿、已投稿、在审等没有公开记录时保留自述状态，同时将外部核验标记为“待核查”，不得推断造假。
- 作者顺序只有在可确定为同一论文且外部作者列表可靠时才判定一致或冲突；身份不确定时标记“待核查”。
- 已核验论文可作为正向可信证据；待核查状态不加分也不扣分。
- 论文信息存在冲突时，人工确认前不自动扣分；确认后只影响相应证据的可信度，不抹除项目能力。
- 简历只有在完整评估成功后才自动进入人才库。仅完成文件解析或评估失败均不算进入人才库。
- OpenAlex、AMiner 等论文外部服务不可用时，不阻塞简历能力评估成功和人才入库。
- 外部核验失败的论文标记为“待核查”并记录失败原因；服务恢复后可以单独重试，不必重跑整份简历评估。
- 只有简历解析、核心能力评分或结果保存失败时，本次简历评估才判定失败。
- 同一候选人的新版简历和重新评估不得覆盖旧记录；人才档案默认展示最新评估，同时保留全部历史版本。
- 每次评估关联对应的简历版本、评分配置版本和评估时间，并支持对比能力与证据变化。
- 简历评估流程增加“入库身份归并”节点，在新建人才档案前判断简历是否属于已有人物。
- 入库身份归并先使用邮箱、ORCID、AMiner ID 等稳定标识，再由 AI 综合姓名变体、教育/工作机构、时间线、研究方向和论文等信息进行模糊身份对齐。
- AI 身份归并必须输出判断、置信度、支持证据和冲突点；自动归并与人工确认的具体边界仍待确认。
- 入库身份归并在能力评分前执行，但只向后续流程提供人物主档 ID 和身份判断，不把历史分数、历史评估结论或 HR 跟进状态注入本次评分上下文。

#### 2.1.1 Track 推荐与研究组匹配

- 当前简历评估只输出基于简历能力证据的宽泛 Track 推荐；Track 推荐属于评估结果，可以继续实现。
- Track 推荐不等于具体研究组匹配，不得在界面、API 或报告中将二者混称。
- 具体研究组匹配依赖 HR 与各研究组确认后的要求；在需求尚未取得前，系统不得自行猜测研究组标准，也不得生成虚假的匹配分。
- 未配置研究组要求时，系统统一返回“研究组匹配尚未配置”，同时保留已有 Track 推荐。
- 研究组匹配未来作为独立模块接入，读取已经完成的能力评估与证据，但不修改原始能力分数、Track 推荐、论文核验或 HR 跟进状态。
- 研究组要求需要版本化保存，并区分必需条件、偏好条件、研究主题、排除条件和证据要求。
- 研究组匹配结果应包含匹配程度、符合项、缺失项、不确定项、引用证据和所使用的需求版本；一个候选人可以同时匹配多个研究组。
- 现有六个 Track 可以用于粗粒度候选范围缩小，但不能替代具体研究组要求或直接决定最终匹配结果。

### 2.2 人才知识 Agent 与已知人物调查

- 已知人物调查不再提供独立的固定表单、页面或专用产品入口，由人才知识 Agent 的对话问答完整覆盖。
- 用户可以输入任意自然语言提示，AI 先判断用户意图，再自行选择人才库查询、AMiner、OpenAlex 或智谱 Web Search 等工具。
- 人才知识 Agent 使用 LangGraph 搭建可追踪的工作流，至少覆盖意图识别、身份解析、库内检索、工具选择、外部调查、证据归一、事实沉淀和带来源回答。
- 本阶段只调查一个可识别的已知人物，不实现按研究方向批量发现未知人才。
- 调查输入允许自然语言自由表达，不要求用户严格填写固定表单或固定关键词。
- 系统利用 AI 从自由输入中提取姓名、机构、研究方向、调查范围和附加检索词。
- 自由输入最终必须解析出一个可确认的具体人物；没有识别到姓名或身份置信度不足时，先要求用户补充或确认，不直接调用外部检索。
- 自由输入不得隐式退化为“按研究关键词发现一批未知人物”；该人才发现用例本阶段不做。
- 学术调查计划使用 AMiner API 获取相关论文信息，用于梳理主要研究范围和关键高引论文。
- 已知人物学术调查以 AMiner 为主要数据源，获取作者画像、研究范围和关键高引论文。
- OpenAlex 在已知人物学术调查中作为补充与交叉核验数据源，用于公开论文信息、作者顺序和撤稿状态等事实。
- AMiner 不可用时，人物学术调查降级使用 OpenAlex 和智谱 Web Search，不得让整个调查任务失败。
- 舆情调查使用公开网络搜索结果，必须保留来源并进行同名消歧。
- 已知人物调查默认同时运行 AMiner 学术画像、OpenAlex 论文补充核验和智谱 Web Search 舆情调查。
- 当用户在自由输入中明确指定“只看论文”“只查舆情”等范围时，AI 可以缩小实际调用范围。
- AMiner、OpenAlex 和智谱 Web Search 三条外部链路独立执行；单一或部分服务失败不拖死整个调查。
- 部分链路成功时，任务状态为“部分完成”或“完成但有警告”，正常返回已有结果，并允许失败链路单独重试。
- 只有人物身份无法识别，或者所有请求均无法执行时，整个人物调查任务才判定失败。
- 一次人物调查只建立或更新人物主档，不自动将该人物加入人才库。
- HR 可以显式执行“加入人才库”，将人物主档关联为人才档案。

### 2.3 人才库

- 人才库应尽可能保存候选人的完整信息与历史，而不只保存评分摘要。
- 可保存的信息包括简历、历次评估、推荐 Track、证据链、论文自述与核验、AMiner 学术画像、关键论文、舆情事实、人工审核、备注和后续研究组匹配。
- 外部信息必须同时保存来源、获取时间、核验状态和历史版本，不能把无来源摘要永久当作事实。
- 外部事实重新检索时不覆盖或删除旧记录；旧事实标记为已过期或已被新版本替代，新事实作为当前待核验版本写入。
- 人才档案默认展示当前版本，但允许查看历史事实和历史人工确认记录。
- 只有明确的数据删除操作才物理删除历史记录。
- 人才有两种进入来源：简历评估成功自动进入；已知人物调查后由 HR 手动加入。
- 人才库必须能区分来源，但来源不是互斥的固定人才类型。
- 人物调查加入的人才后来完成简历评估时，合并为同一个人才档案，并同时保留两种来源。
- 稳定标识一致，或姓名与机构等身份信息可靠匹配时可以自动合并，并记录合并依据。
- 只有姓名相同时不得自动合并，应生成疑似同人建议供 HR 确认。
- 身份信息明显冲突时禁止自动合并；人工合并需要审计记录并支持解除。
- 人才库提供独立的 HR 人工跟进状态，初步状态为：新入库、待联系、已联系、面试中、持续关注、已结束。
- HR 跟进状态与简历能力评估完全独立，不参与能力评分、Track 推荐或论文核验。
- 跟进状态只能人工修改，系统不得根据分数、舆情或其他自动规则切换。
- 每次状态变化保存时间、操作者和备注；只读人才知识库可以查询但不能修改状态。

### 2.4 产品演进方向

- 人才库演进为人才知识库，允许用户用自然语言检索、汇总和比较人才档案。
- 人才知识库第一版确定为只读；对话不能直接修改候选人状态、合并人物、加入或删除人才。
- “只读”特指业务操作只读：人才知识 Agent 不能修改 HR 状态、合并人物、加入或删除人才、确认舆情或修改评分。
- 人才知识 Agent 联网调查后可以追加“待核验外部事实”，但不得覆盖、删除或确认已有事实；事实确认等人工操作只在直观展示界面完成。
- 人才知识库同时提供两种界面：对话问答界面，以及用于列表、筛选、详情和比较的直观展示界面。
- 对话问答与直观展示读取同一套人才档案和证据来源，不形成两套互相矛盾的数据。
- 人才知识库不是本阶段的人才发现功能；它首先面向人才库中已经存在的数据。
- 每个对话结论应能追溯到具体人才档案、评估记录或外部事实。
- RAG 是人才知识库检索与回答生成的优先技术探索方向，但尚未冻结具体切分、索引、召回和重排方案。
- RAG 的向量化固定使用智谱远程 `embedding-3`，不部署本地 Embedding 模型，也不为本地模型预留 Provider 抽象。
- Embedding 调用使用智谱开放平台 `/api/paas/v4/embeddings` 接口；若现有 `Z_AI_API_KEY` 是开放平台 API Key 且具备模型额度，则与 Web Search 共用该 Key。
- `embedding-3` 固定使用 1024 维，在语义检索精度、存储和检索成本之间取平衡。
- 按官方接口限制，单条输入最多 3072 tokens，一次请求最多 64 条；RAG 切片和批处理必须遵守该限制。
- 向量记录必须保存模型名、维度和索引版本；模型或维度变化时重新构建全部向量索引。
- RAG 必须使用独立的轻量向量数据库服务，不把向量直接存入 MySQL，也不使用 Flask 进程内存承担正式向量检索。
- 向量数据库确定使用 Qdrant。
- MySQL 是人才档案、原文、证据、外部事实和核验状态的唯一业务数据真源。
- Qdrant 只保存可重建的文本块向量、检索 payload 和对应的 MySQL 记录 ID，不得成为任何人才事实的唯一保存位置。
- 数据更新或删除先提交 MySQL，再同步 Qdrant；同步失败写入可重试任务。
- Qdrant 索引丢失或模型版本变化时，从 MySQL 原文重新调用 `embedding-3` 构建全部索引。
- 人才知识库采用 MySQL 与 Qdrant 混合查询：精确字段、数量、状态和排序由 MySQL 处理，开放式语义检索由 Qdrant 处理。
- 混合问题先用 MySQL 缩小候选人范围，再使用 Qdrant 在该范围内进行语义检索。
- 人才知识库对话允许主动调用 AMiner、Web Search 等外部工具，但必须优先检索和使用人才库已有内容。
- 库内信息足以回答时不调用外部工具；信息缺失、明显过期或用户询问最新情况时，可以主动进行外部补充调查。
- 回答必须区分库内既有事实与本次联网获得的新事实，并分别标注来源和获取时间。
- 主动联网获得的新信息自动写回人才知识库，但初始状态必须是“待核验外部事实”。
- 待核验外部事实必须保存原始来源、获取时间和查询条件，并对重复事实进行归并。
- 新事实不得直接覆盖已经人工确认的资料；与旧事实冲突时两者并存，并生成待人工确认项。
- 只有经过人工确认后，待核验外部事实才能升级为可信档案事实。
- RAG 可以召回已确认、待核验和冲突事实，但必须把核验状态保留到最终回答中。
- 待核验事实只能以“尚未人工确认”的措辞引用；冲突事实必须同时展示不同来源，AI 不得擅自选择一个作为真相。
- 用户明确只询问已确认信息时，检索层排除待核验和冲突事实。
- 对话引用必须携带来源、获取时间和核验状态。
- 不接入智谱网页读取 MCP 的 `webReader`，继续保留现有智谱 Web Search 作为公开网页与舆情检索服务。

### 2.5 前端方向

- 人才知识库同时具备对话界面和直观展示界面，两者服务于不同查询方式。
- 前端提供独立的人才库页面，并按人才来源分为两类视图：简历评估进入的人才，以及人物调查后人工加入的人才。
- 两类视图读取同一个 Candidate 主档，不建立两套人才数据。
- 同时具有简历评估和人物调查来源的人才出现在两个来源视图中，并显示两个来源标签，但始终指向同一个人才档案。
- “全部人才”视图和人数统计按唯一 Candidate 去重，不因双来源重复计数。
- 人才库增加人才关系图谱视图，展示人才与学校、机构、研究方向及其他有证据联系之间的关系。
- 相同学校、机构或其他关系的人才应能以颜色、聚类或连线形成直观关联；推荐或匹配方向相同的人才也应能在图中被关联和发现。
- 学校、机构和研究方向建模为独立实体节点；人才通过共同实体节点形成聚类，不为同学校或同方向的所有人才建立两两直接连线。
- 只有共同论文、共同项目、真实合作或人工确认关系，才建立“人才到人才”的直接边。
- 结构化已确认关系和带可靠来源的合作关系使用实线，并可查看证据来源。
- AI 推断但尚未人工确认的关系使用虚线并标记“待核验”；没有证据来源的关系不进入图谱。
- 被新证据否定的关系保留历史记录，但从当前关系图中隐藏。
- 人才节点颜色用于表达学校归属，相同学校使用相同颜色；学校数量较多时需要稳定的颜色分配、图例和交互高亮辅助辨识。
- 人才节点形状用于表达主要匹配或推荐方向；次要方向不能再占用节点形状，具体表达方式仍待确认。
- 人才拥有多段教育经历时，当前就读学校优先决定节点颜色；已经毕业则使用最高学历学校。其他学校关系继续通过学校实体节点和连线保留。
- 图谱的次要方向表达、颜色调色板、布局、聚类和交互细节推迟到该功能实际开发时再确认，当前不继续展开。
- 关系图谱与列表、详情、比较和对话界面读取同一套人物、人才、证据和方向数据。
- 图谱的节点类型、边类型、颜色语义、关系置信度和稠密关系降噪方式仍待确认。
- 前端视觉风格初步采用 Material Design 3；这是当前设计倾向，实施前仍需结合现有技术栈形成具体组件与设计令牌方案。

### 2.6 访问权限

- 平台是内部工具，不设计多角色、多层级的数据权限模型。
- 使用一个密码完成访问鉴权；鉴权成功后获得平台全部信息与功能权限。
- RAG、人才档案、HR 备注、论文核验和舆情信息使用同一访问权限，不做字段级过滤。
- 除登录接口和健康检查外，所有页面、后端 API 和 SSE 流都必须鉴权。
- 访问密码从环境变量读取，不得写入前端或提交到仓库。
- 登录成功后使用服务端签名的会话 Cookie，并支持会话过期和主动退出。
- 未鉴权的 API 返回 `401`，未鉴权的页面请求跳转登录页。

### 2.7 全局服务配置

- 后续增加一个内部配置界面，用于配置 LLM、AMiner、智谱搜索和 Embedding 等外部服务的 Key、Base URL、模型名与 Provider。
- 配置是服务器级全局配置，所有通过内部密码鉴权的使用者共享同一套配置，与当前单实例逻辑一致。
- Key 不得硬编码进代码或前端资源；配置界面由后端更新服务器上的 `.env`。
- 浏览器前端不得直接读取或下载 `.env`；后端配置接口只能返回非敏感配置和 Key 的“已配置/未配置”或脱敏状态。
- `.env` 更新后的运行时加载、原子写入、失败回滚和是否需要重启仍待确认。

## 3. 当前建议的数据关系

```text
Person 人物主档
  ├─ 人物调查历史
  ├─ 学术与舆情外部事实
  └─ Candidate 人才库身份（可选，一人至多一个）
       ├─ CandidateSource: resume_evaluation
       ├─ CandidateSource: person_investigation
       ├─ 简历与历次评估
       └─ HR 管理记录
```

论文核验是简历评估的辅助链路，其结果可以保存在完整人才档案中，但不会成为自动分组或录取规则。AMiner 人物学术画像属于已知人物调查；人物被加入人才库后，人才档案可以关联并展示这些历史信息。

## 3.1 论文与公开信息服务的用例归属

| 服务 | 简历评估 | 已知人物调查 | 人才知识库对话 |
|---|---|---|---|
| AI 语义提取 | 从简历理解论文自述状态、作者角色和上下文 | 从自由输入提取人物身份、调查范围和检索条件 | 理解问题、组织库内检索和生成带引用回答 |
| OpenAlex | 主要用于核验公开发表信息和作者顺序 | 补充、交叉核验论文公开事实 | 仅在库内不足且问题涉及具体论文事实时补充调用 |
| AMiner | 默认不参与简历论文核验 | 主要用于作者画像、研究范围和关键高引论文 | 仅在库内不足且问题涉及人物学术画像时补充调用 |
| 智谱 Web Search | 默认不参与简历能力评分；必要时只作公开来源补充 | 用于舆情检索，并在 AMiner 不可用时辅助学术画像 | 仅在库内不足、需要最新公开信息或舆情事实时补充调用 |

人才知识库不另造一套论文服务。它先使用已经沉淀的数据，确需联网时再根据问题类型调用对应服务，并把新结果按“待核验外部事实”保存。

## 4. 与现有文档和代码的已知冲突

- 旧设计使用“简历初筛”“嘉宾画像”等术语，当前统一为“简历评估”和“已知人物调查”。
- 旧设计把已知人物调查作为独立功能入口，当前改由人才知识 Agent 的对话和工具调用覆盖。
- 旧设计存在按总分写入 `shortlisted / alternative / rejected` 的自动分组，当前决策明确取消。
- 旧设计曾让舆情作为推荐闸门或自动结论，当前评分、舆情和未来研究组匹配保持独立。
- 旧设计把评估过的嘉宾直接纳入人才库，当前改为人物调查后必须由 HR 显式加入。
- 当前论文状态模型仍含固定关键词归一化逻辑，需要改为 AI 语义判断主导、结构校验兜底。
- 当前人物调查后端入口仍以姓名、机构和方向字段为主，自由自然语言输入尚未落实。
- 当前 AMiner 论文检索接口尚未正式接入，关键高引论文能力依赖接口开通与实现。
