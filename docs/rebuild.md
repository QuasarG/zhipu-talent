# 面试准入评估重建方案

> 状态：已确认，作为后续重建的唯一执行依据
> 日期：2026-08-25
> 领域语言：[CONTEXT.md](./CONTEXT.md)
> 界面准则：[design/DESIGN.md](./design/DESIGN.md)

本文定义面试准入评估、岗位评估卡和统一 LLM 运行轨迹的目标状态。当前代码仍是过渡实现，不能据此反推本文已经落地。

> 实施状态（2026-08-25）：第一条可运行纵切已经落地，包括独立候选人–JD 当前报告、岗位卡生成与质检、
> 多节点评估、确定性准入、统一并发/熔断、批次取消与输入锁、管理员强制重评、新准入页面、JD 显式选择、
> 运行轨迹和内嵌导入卡。旧简历评估链仍作为兼容功能保留，后续需单独按“简历–JD 搭配”目标重建；
> 失败后从精确节点续跑、结果展示的进一步产品化和生产校准仍属于下一阶段，不能把当前纵切误写成全部完成。

## 1. 重建目标

系统接收一批简历和用人方明确选择的一个或多个 JD，针对每个候选人–JD 配对回答：

> 该候选人是否具备完成这个岗位核心任务的能力，值得进入面试？

重建必须同时解决以下问题：

- 同一份简历重复运行时，事实识别和评分结构不能大幅漂移。
- 学历、专业只是背景证据，不是不可补偿的硬门禁。
- 没有在技能栏写出 PyTorch，不等于候选人不会 PyTorch。
- 论文、项目和工作经历中的实际问题、行动、责任与成果必须进入能力判断。
- 证据提取不能成为有损漏斗，后续推理节点必须看到完整脱敏简历。
- 模型调用可以并行，但不能由候选人和任务两层并发相乘后再次触发 429。
- 无论进入或不进入面试，结果都必须完整、可追溯、可解释。

## 2. 产品边界

### 2.1 独立功能

面试准入评估独立于人才库中的简历评估：

- 面试准入评估：针对候选人–JD 配对做二元进面决策。
- 简历评估：后续对人才库已有简历做评价、JD 匹配与关联，本次不重建。

### 2.2 不评估的内容

以下候选人可用性信息不进入本系统：

- 到岗时间；
- 可实习时长；
- 工作地点；
- 薪资或类似履约条件。

系统不生成 `hold` 或“待确认”准入结论。运行状态可以失败或取消，但业务结论只有“进入面试”和“不进入面试”。

### 2.3 最小决策单元

最小决策单元是候选人–JD 配对。一次评估批次由一批待筛简历和从 JD 池显式选择的一个或多个 JD 组成，并对选中集合形成配对判断。

系统不生成脱离 JD 的候选人总体准入结论，也不在候选人通过多个 JD 时自动选择“最佳 JD”。

## 3. JD 池与岗位评估卡

### 3.1 JD 池行为

- JD 不再拥有“激活 / 未激活”状态。
- JD 是否参与评估，仅由启动本次批次时的显式选择决定。
- JD 池只负责保存、编辑和归档可选择的 JD。

### 3.2 岗位补充要求

每个 JD 有一份可维护的当前补充要求清单：

- 可以多次添加；
- 已添加的要求可以编辑或删除；
- 不保留旧清单历史；
- 修改补充要求与重新生成岗位评估卡是一个原子动作；
- 新卡生成失败时，原清单、原卡和原评分有效性保持不变；
- 新卡生成成功时整体替换，并将该 JD 的当前评估报告标记为失效。

### 3.3 岗位评估卡结构

岗位评估卡由 JD 原文和当前补充要求自动生成，无需人工审批。建议结构如下：

```json
{
  "jd_id": "jd_xxx",
  "role_summary": "岗位主要解决的问题与结果责任",
  "criteria": [
    {
      "id": "criterion_1",
      "title": "分析 Agent 失败模式",
      "description": "识别主要失败类型、提出原因假设并设计验证",
      "importance": "primary",
      "evidence_guidance": "允许研究实验、系统诊断和相邻评测工作的等价证据",
      "anchors": {
        "2": "参与过错误分类、效果诊断、对照实验或类似工作",
        "3": "能独立构建分析框架、定位主要失败类型并验证原因",
        "4": "在多个复杂场景中持续完成失败分析并推动系统迭代"
      }
    }
  ]
}
```

约束：

- 通常 3–5 项核心任务，硬上限 6 项。
- 同一工作闭环中的工具或操作不能拆成多个重复评分项。
- 每项描述岗位实际要完成的工作，不写成技能关键词清单。
- 数字、工具名和特定论文只能作为可能证据，不能成为必选格式。
- 学历和专业只作为背景证据。
- 候选人可用性条件必须排除。

### 3.4 任务重要性

核心任务只有三档固定重要性：

| 重要性 | 系数 | 含义 |
| --- | ---: | --- |
| 首要 `primary` | 3 | 岗位成立的核心工作 |
| 主要 `major` | 2 | 岗位日常的重要工作 |
| 补充 `supporting` | 1 | 有价值但可以被其他能力补偿的工作 |

重要性在岗位评估卡生成时固定，同一张当前卡对所有候选人一致。只有重新生成岗位评估卡才会变化。

### 3.5 自动质检

岗位评估卡必须经过自动质检：

1. 生成节点产出候选卡。
2. 质检节点检查任务覆盖、重复、粒度、错误门槛、权重和任务化锚点。
3. 发现问题时携带具体反馈回到生成节点，最多修正一次。
4. 仍不合格则本次生成失败，不替换当前卡。

岗位卡生成频率远低于候选人评分，可以使用额外一次模型复核换取全体候选人的一致基准。

## 4. 评分语义

### 4.1 通用能力等级

每个核心任务使用统一的 0–4 等级：

| 等级 | 名称 | 通用含义 |
| ---: | --- | --- |
| 0 | 无证据 | 简历没有可支撑该任务的相关经历 |
| 1 | 相关基础 | 有相邻知识或背景，但没有实际完成过类似任务 |
| 2 | 实际参与 | 做过相关工作，有具体行动或产出，但范围、独立性或复杂度有限 |
| 3 | 独立胜任 | 有高度相似的项目证据，方法、本人责任和结果形成完整闭环 |
| 4 | 成熟胜任 | 在多个或复杂场景中持续完成类似任务，体现端到端负责或可迁移方法能力 |

通用等级保证不同 JD 使用同一尺度。岗位评估卡中的任务化锚点只是对通用等级的岗位化翻译，不形成第二套分数。

### 4.2 证据类型

能力映射区分三类证据：

| 类型 | 定义 | 评分作用 |
| --- | --- | --- |
| 直接证据 | 实际完成过相同或高度相似的核心任务 | 可直接支撑相应能力等级 |
| 可迁移证据 | 场景不同，但问题结构、方法或责任范围可迁移 | 结合关联理由和迁移边界支撑评分 |
| 背景证据 | 学历、专业、技能关键词或方向兴趣 | 只能帮助理解，不能单独支撑等级 2 以上 |

同一个完整项目或论文可以用不同理由支撑多个核心任务，但不能复制成多个独立来源来虚增证据数量或置信度。

### 4.3 证据保真原则

证据是输出约束和原文索引，不是后续节点的输入围栏：

- 所有能力推理节点必须同时读取完整脱敏简历和结构化简历。
- 前置能力映射遗漏某项成果时，任务评分节点可以直接从完整简历补充评分证据。
- 每项评分必须提供原文引用和所在简历区段。
- 引用必须经过确定性可追溯校验。
- 不能因为技能栏缺少工具名，就将工具能力判定为不会或硬性不足。

### 4.4 证据置信度

证据置信度只有高、中、低三档：

- 高：完整、直接、可追溯的相似任务证据，行动、责任和结果清楚。
- 中：直接证据不完整，或存在多项较强的可迁移证据。
- 低：主要依靠相邻经历推断，证据较少或贡献边界模糊。

置信度只展示，不参与总分或准入公式。证据不足以支撑当前等级时，应直接降低能力等级，不能再通过置信度暗扣第二次。

### 4.5 总分与准入规则

模型不直接生成百分制总分。代码按以下公式换算：

```text
单项百分制 = 能力等级 / 4 × 100
总分 = Σ(单项百分制 × 任务系数) / Σ任务系数
```

进入面试必须同时满足：

1. 每一个首要任务能力等级都不低于 2；
2. 加权总分不低于 50。

其他任务允许相互补偿。最终决策由确定性代码完成，模型无权绕过规则。

## 5. 候选人–JD 评估工作流

### 5.1 总图

```text
pair_preparer
      ↓
capability_mapper
      ↓
criterion_assessor × 3–6
      ↓ 受全局并发池调度
evidence_validator
      ↘ 引用失败时，仅对应任务 repair 一次
assessment_reviewer
      ↓
decision_policy
      ↓
report_assembler
```

核心任务分别调用模型，允许并行；它们不共享可变上下文，也不按候选人创建私有并发池。

### 5.2 `pair_preparer`

职责：

- 获取候选人、JD、当前岗位评估卡和当前评估规则；
- 对本轮使用的简历、JD、补充要求和岗位评估卡加输入锁；
- 生成完整脱敏简历文本和结构化简历；
- 创建候选人–JD 运行记录；
- 不调用 LLM，不做能力判断。

脱敏后的完整文本必须保留项目、论文、经历的上下文和内部逻辑，不能再次拍平成关键词集合。

### 5.3 `capability_mapper`

职责：

- 同时读取完整脱敏简历、结构化简历和完整岗位评估卡；
- 为每个核心任务寻找直接、可迁移和背景证据；
- 展示“证据 → 关联理由 → 迁移边界”的结构化推理摘要；
- 可以保持一定创造力，识别非字面、跨技术栈或跨场景的能力对应关系；
- 不给能力等级，不做准入决策。

该节点可使用略高于评分节点的 temperature，但必须受结构化输出和原文引用约束。

### 5.4 `criterion_assessor`

每个核心任务一个独立评分调用。每次调用都接收：

- 完整脱敏简历；
- 结构化简历；
- 完整岗位评估卡；
- 当前任务的通用与任务化锚点；
- 能力映射结果；
- 已验证的论文等补充事实，但不得用外部核验缺失反向否定简历自述。

输出建议：

```json
{
  "criterion_id": "criterion_1",
  "level": 3,
  "confidence": "medium",
  "evidence": [
    {
      "kind": "transferable",
      "section": "论文与项目",
      "quote": "候选人简历中的原文片段",
      "relevance": "为何支撑当前任务",
      "boundary": "尚未被证据覆盖的迁移边界"
    }
  ],
  "rationale": "为何符合等级 3 而不是 2 或 4",
  "capability_gap": "当前最主要的能力缺口",
  "interview_focus": ["进入面试后需要验证的问题"]
}
```

评分节点可以纠正能力映射的遗漏，但不能修改任务定义或权重。

### 5.5 `evidence_validator` 与局部修正

证据校验由确定性代码完成：

- 检查原文引用能否在脱敏简历中定位；
- 检查引用数字和关键实体是否被模型改写；
- 检查 evidence kind、区段和引用字段是否完整；
- 不判断候选人能力高低。

某项评分存在无法追溯的关键引用时：

1. 仅把该任务和具体错误反馈给评分节点；
2. 最多纠错重评一次；
3. 再次失败时移除无效证据；
4. 剩余证据不足以支撑等级 2 以上时降到 1 或 0；
5. 其他核心任务不重跑。

### 5.6 `assessment_reviewer`

前端称为“评分总审”。它重新读取完整脱敏简历、岗位评估卡和全部任务评分，检查：

- 能力等级是否符合统一与任务化锚点；
- 理由、证据和等级是否自相矛盾；
- 是否遗漏显著强证据；
- 同一证据是否被伪装成多个独立来源；
- 跨任务复用是否有不同且合理的关联理由；
- 不同任务评分是否出现明显失衡。

评分总审可以纠错，但每次修改必须记录：

- 任务 ID；
- 原等级与新等级；
- 原置信度与新置信度；
- 修改原因；
- 支撑修改的原文证据。

总审不能修改岗位任务、重要性或准入公式，也不能无审计记录地重写整份结果。

### 5.7 `decision_policy` 与 `report_assembler`

`decision_policy` 使用固定公式计算总分和二元准入结论。`report_assembler` 不再调用 LLM，只组装：

- 进入 / 不进入面试；
- 总分及公式明细；
- 每项核心任务的等级、置信度、证据、关联理由和迁移边界；
- 评分总审的纠错记录；
- 核心优势与能力缺口；
- 进入面试者的针对性面试重点；
- 实际使用模型与降级信息；
- 当前 LLM 运行轨迹。

不进入面试者同样拥有完整报告，但不生成多余的面试问题。

## 6. LLM 调度、限流与降级

### 6.1 单一全局并发池

所有通过统一 LLM 客户端发出的请求共享全局并发上限 5。不得再出现“批量候选人并发 × 单候选人任务并发”的乘法。

映射、核心任务评分、局部重评、评分总审、岗位卡生成和质检都使用同一个调度入口。队列必须是 work-conserving：有额度就执行，但任何调用方不能绕过额度自建并发池。

### 6.2 5.3 → 5.2 熔断降级

- 主模型为 GLM-5.3，备用模型为 GLM-5.2。
- 只有明确的 HTTP 429 或业务错误码 `1302` 触发限流熔断。
- 当前失败请求立即改用 5.2。
- 熔断打开后的短时间内，所有新调用直接使用 5.2，不再反复撞击 5.3。
- 冷却后只放行一个 5.3 探测请求；成功则恢复，失败则继续降级。
- 初始冷却时长建议为可配置的 60 秒，后续以真实速率限制调整。
- 5.3 使用启用思考的调用参数，5.2 使用禁用思考；业务 payload 和 JSON schema 不变。

同一次候选人–JD 评估可以混用 5.3 和 5.2。已完成节点不重跑，所有节点必须记录实际模型、降级原因和时间。

非限流错误不得误触发模型降级，应走各自的超时、网络或格式修复策略。

## 7. 状态、有效性与权限

### 7.1 只保留当前报告

- 每个候选人–JD 配对只保留一份当前报告和对应运行轨迹。
- 不保留可浏览的历史评分、历史岗位卡或版本链。
- 系统只记录当前报告是有效还是失效，不向用户显示版本号。
- 重评成功后，新报告和新轨迹直接覆盖旧内容。
- 重评失败时，原有效报告保持不变。

### 7.2 失效触发

- 简历内容变化：该候选人的所有 JD 报告失效。
- 岗位评估卡重新生成：该 JD 的所有候选人报告失效。
- 评分语义或准入规则变化：全部当前报告失效。
- 普通 UI、动画、错误文案或调度实现变化：不触发失效。

### 7.3 输入锁

评估运行期间禁止修改本轮使用的简历、JD、补充要求和岗位评估卡。限制必须由后端校验，不能只禁用前端按钮。

- 修改某份简历前，需停止该候选人的所有运行中 JD 配对。
- 修改某个 JD 前，需停止所有正在使用该 JD 的配对。
- 无关候选人和无关 JD 不受影响。

### 7.4 取消与失败

取消支持单个候选人–JD 配对和整个批次：

- 未发出的工作停止；
- 已在途结果返回后丢弃；
- 本轮全部中间产物作废；
- 不生成半成品报告；
- 解除输入锁。

技术失败不等于能力 0，也不生成待确认结论：

- 失败配对标记为运行失败；
- 其他配对继续；
- 输入未变时可以从失败节点重试；
- 输入已变时丢弃中间产物并从头运行。

### 7.5 幂等与强制重评

普通用户不能对仍然有效的候选人–JD 报告反复运行。只有失效、失败或缺少报告时可以评估。

当前仅用户 `guozexin` 拥有“允许强制重评”的个人设置开关：

- 其他用户看不到该设置和操作；
- 开关关闭时，`guozexin` 也遵循普通规则；
- 强制重评成功后覆盖当前报告；
- 强制重评失败时保留当前有效报告；
- 不保留两次结果的历史对比。

## 8. 批次与结果页面

### 8.1 启动批次

启动面试准入评估时显式选择：

- 一批待筛简历；
- JD 池中的一个或多个 JD。

提交前展示：

```text
N 份简历 × M 个 JD = N×M 个候选人–JD 配对
```

JD 池中的状态不再隐式决定本批范围。

### 8.2 结果主视角

批次结果按 JD 组织：

- 每个选中 JD 一个结果页签或分区；
- 进入面试者在前，按总分排序；
- 不进入面试者在后，仍显示总分、首要缺口和完整报告入口；
- 同一候选人可以出现在多个 JD 下；
- 不生成跨 JD 总分、最佳 JD 或排他分配。

## 9. 统一 LLM 运行轨迹

### 9.1 视觉原则

所有 LLM 工作必须显示真实运行步骤，采用“轻度知识图谱感”的统一视觉语言：

- 固定布局，不允许拖拽；
- 节点从上到下随真实运行依次生长；
- 并行节点在同一纵向任务组内逐个出现并可同时点亮，不做横向无限画布；
- 连线只表达真实依赖，不作装饰；
- 节点默认显示业务名称、状态和一句摘要；
- 展开后显示结构化中间产物、证据、纠错记录、实际模型和错误；
- 不展示原始 chain-of-thought、完整 prompt、密钥或无用内部日志；
- 支持键盘、屏幕阅读器和 reduced motion。

### 9.2 两类布局

有持久结果的工作流使用纵向节点图，例如岗位卡生成和面试准入评估。当前有效结果对应的轨迹与报告一起保存，覆盖结果时一并覆盖。

对话型 Agent 使用消息内嵌节点链：只在当前一轮调用运行时展示，回答完成后节点链消失，不长期保留在聊天记录中。

### 9.3 简历导入运行卡

简历导入不再使用浮动遮罩。运行卡临时插入简历评估页左侧候选人列表底部、固定在“导入简历 / 批量操作”工具栏上方：

- 候选人列表缩短并独立滚动，运行卡始终可见；
- 卡片按“读取文件 → 识别内容 → 结构化解析 → 保存候选人”自上而下生长；
- 批量导入显示总体进度，并可查看当前文件；
- 运行期间禁止关闭；
- 全部成功后显示完成态约 2 秒并自动移除；
- 部分或全部失败时保留失败文件、重试和确认关闭入口；
- 运行卡和轨迹不进入人才档案，不形成历史版本。

### 9.4 面试准入评估轨迹

评估轨迹位于结果区域的同级“运行过程”视图，自上而下展示：

```text
准备输入
  ↓
能力证据映射
  ↓
核心任务评分组（全局并发池调度）
  ↓
证据校验与局部修正
  ↓
评分总审
  ↓
准入决策与报告
```

点击核心任务评分节点必须能看到“证据 → 关联理由 → 迁移边界 → 等级与置信度”。评分总审节点必须展示所有纠错审计。

## 10. 建议数据契约

### 10.1 当前岗位卡

```text
jd_entry
  raw_text
  supplements_json
  assessment_card_json
  card_status: ready | generating | failed
  updated_at
```

不再需要 `active` 状态。归档只表示不再出现在默认选择列表，不等于历史评估范围。

### 10.2 当前配对评估

```text
candidate_jd_assessment
  candidate_id
  jd_id
  status: queued | running | completed | failed | cancelled
  is_valid
  decision: interview | no_interview | null
  total_score
  task_assessments_json
  review_corrections_json
  interview_focus_json
  model_usage_json
  run_trace_json
  created_at
  updated_at
```

`candidate_id + jd_id` 应保持当前报告唯一性。批次与配对运行记录可以独立建表，但不能把多份历史报告重新暴露为产品版本链。

### 10.3 运行节点事件

统一事件至少包含：

```text
run_id, node_id, parent_id, label, status,
summary, detail, model, fallback_reason,
started_at, completed_at, error
```

前端只能根据真实事件生长节点，不使用定时器伪造步骤。

## 11. 验收标准

### 11.1 业务语义

- 同一候选人在不同 JD 下产生独立结果。
- 学历和专业不作为硬门禁。
- 到岗和实习时长不进入评估。
- 最终没有 `hold` 或待确认状态。
- 首要任务低于 2 时不进入面试。
- 总分低于 50 时不进入面试。
- 不进入面试者仍有完整信息展示。

### 11.2 仲奕杰回归案例

真实回归夹具必须覆盖：

- 同济大学人工智能博士、南京大学计算机硕士被识别为背景事实；
- WWW、ACL、CVPR、IJCAI 等论文和一作信息进入能力映射；
- Agent、RAG、评测、长期记忆和大规模数据经历进入对应核心任务；
- 未在技能栏显式写 PyTorch，不得被推断为不会 PyTorch；
- 理由、证据和等级不能出现“理由明确满足但状态未知”的矛盾；
- 强制重评时结构、门槛和主要证据归属应保持稳定。

### 11.3 运行与限流

- 任意时刻实际 LLM 并发不超过 5。
- 多候选人和多任务并发不会相乘绕过限制。
- 429 / 1302 触发全局短时降级到 5.2。
- 冷却期内不持续请求 5.3，恢复探测只有一个。
- 混用模型的节点留有完整记录。
- 单任务证据修正最多一次。
- 单配对失败不拖垮整个批次。

### 11.4 前端

- JD 选择发生在启动批次时，不存在“激活 JD”联动。
- 评估图从上到下依真实事件生长且不可拖拽。
- 对话节点链在当前轮结束后消失。
- 面试准入当前轨迹随当前报告保留。
- 导入运行卡嵌入左侧队列底部，运行中不可关闭，成功自动退场，失败可重试。
- 所有节点的失败、取消、降级和模型信息可访问且不只依赖颜色表达。

## 12. 实施顺序

1. 清理旧评估数据模型和 JD `active` 语义，建立当前岗位卡与当前配对评估契约。
2. 抽出统一 LLM 执行入口：全局并发 5、错误分类、5.2 熔断降级和模型留痕。
3. 实现岗位卡生成、质检、原子替换和关联评估失效。
4. 先写仲奕杰等回归测试，再实现能力映射、并行任务评分、证据校验和评分总审。
5. 接入确定性总分与二元准入策略。
6. 实现批次选择、按 JD 结果列表、取消、输入锁和强制重评权限。
7. 建立统一 LLM 运行事件协议和纵向生长组件。
8. 改造面试准入运行图、简历导入内嵌卡和对话临时节点链。
9. 完成专项、全仓、并发、熔断和前端构建验证后再部署。

实施过程中，任何为了兼容旧 Track 评估而重新引入通用六维、全局激活 JD、`hold` 状态或证据唯一输入的方案，都视为偏离本设计。
