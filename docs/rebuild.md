# 人才评估重建方案

> 状态：已确认方向，作为下一阶段产品和工作流重建依据
> 日期：2026-08-26
> 领域语言：[CONTEXT.md](./CONTEXT.md)
> 界面准则：[design/DESIGN.md](./design/DESIGN.md)

本文重新定义人才评估产品的入口、信息架构和后续 Agent 演进方向。它取代旧版“面试准入评估重建方案”中关于管理员强制重评、旧简历评估链和报告组织方式的描述。

当前已上线的面试准入纵切继续作为运行基础，包括岗位评估卡、候选人–JD 配对、证据评分、纵向运行图、取消与输入锁、全局并发限制、全用户重评和配对互斥锁。本文描述的是下一阶段的产品整合目标，不把尚未实现的能力评估写成已完成。

## 1. 先确定产品边界

系统最终提供一个统一的“人才评估”入口，入口下有两个业务子界面：

1. **面试准入**：判断某个候选人是否值得进入某个 JD 的面试。
2. **能力评估**：判断某个候选人自身具备怎样的稳定能力结构。

二者共享候选人、简历、证据和运行基础设施，但不共享决策对象：

| 子界面 | 最小评估单元 | 要回答的问题 |
| --- | --- | --- |
| 面试准入 | 候选人 × JD | 这个人是否具备完成该岗位核心任务的能力，值得投入面试资源？ |
| 能力评估 | 候选人 | 这个人有哪些可复用的能力、边界和证据？ |

不能把两者合成一个无目标的总分，也不能让能力评估分数直接替代某个 JD 的准入判断。

### 1.1 旧“简历评估”退出主线

原有简历评估过程、Track 推荐和旧通用维度评分不再作为新的产品目标。后续它们会被能力评估工作流替代。

- 旧数据暂不物理删除，避免破坏人才档案和已有引用。
- 旧结果不冒充新的能力评估结果。
- 新页面不继续扩展旧的评估过程图和旧评分语义。
- 能力评估的维度、证据结构和评分规则需要单独重建，确认前只提供明确的占位状态。

## 2. 推荐的产品形态：统一外壳，两个子界面

不建议把两个工作流硬塞成一张没有层次的页面，也不建议继续维护两个互不关联的顶级入口。推荐采用与人才问答页相似的结构：

```text
人才评估
├── 面试准入
└── 能力评估
```

统一外壳负责候选人导航、导入、运行状态、持久化和跨页面关联；子界面负责各自的业务内容和操作。

建议路由为：

```text
/talent-evaluation/admission
/talent-evaluation/capability
```

当前的 `/interview-admission` 和 `/resume-evaluate` 作为迁移兼容入口，逐步重定向到统一外壳，不再分别发展新的导航和数据模型。

### 2.1 共用左侧：候选人文件夹

左侧不再按“报告列表”平铺，也不显示候选人内部 ID。每个人是一个小文件夹，文件夹下挂该人的评估对象：

```text
候选人 A
├── 能力评估
├── 预测训练数据算法工程师
├── 多模态生成算法研究
└── 算法工程师（Agent 评测方向）

候选人 B
├── 能力评估
└── 预测训练数据算法工程师
```

规则：

- 文件夹标题始终使用候选人姓名；姓名为空时才使用明确的“未命名”提示，不能把 ID 当姓名展示。
- JD 子项只表示该候选人与该 JD 的当前准入评估，不表示候选人被分配到该岗位。
- 没有报告的 JD 子项可以显示“未评估”，但不伪造报告卡片。
- 进入或不进入面试的结果都保留入口，不能只列通过者。
- 候选人从待评估队列移出后，已存在的报告仍应能通过人才档案或评估入口找到，并继续显示姓名。

### 2.2 导入简历

“导入简历”按钮迁移到左侧候选人卡片底部，作为人才评估的共用动作。

导入卡片继续遵循已经确认的交互：

- 卡片临时插入左侧列表底部，不使用浮动遮罩。
- 导入运行期间不可关闭。
- 按“读取文件 → 识别内容 → 结构化解析 → 保存人才档案”自上而下显示真实进度。
- 每份简历落库后立即在左侧出现候选人文件夹。
- 成功后自动退场；失败时保留失败文件和重试入口。
- 导入运行卡本身不形成历史评估报告。

### 2.3 共用状态与持久化

统一外壳保存以下状态：

- 当前子界面；
- 当前候选人；
- 当前 JD；
- 当前批次和运行 ID；
- 当前节点详情；
- 导入运行状态。

切换子界面、刷新或短暂离开页面都不能丢失正在运行的工作流。持久化以服务端运行记录为准，浏览器只保存恢复所需的轻量上下文。

## 3. 面试准入子界面

面试准入仍是 JD 驱动的独立业务功能。

### 3.1 默认是浏览和查看

进入面试准入后，默认展示候选人文件夹和已有 JD 子项，而不是直接把用户塞进一个报告选择器。

选中候选人根节点时，可看到该候选人的基本档案摘要；选中某个 JD 子项时，进入该候选人–JD 的准入报告和运行图。

### 3.2 新建批次是明确的临时模式

“新建准入评估”进入批量选择模式：

- 选择一批候选人；
- 从 JD 池显式选择一个或多个 JD；
- 提交前展示 `候选人数 × JD 数 = 配对数`；
- 启动后回到对应候选人文件夹，并可查看每个 JD 子项的实时状态。

批量选择模式可以暂时占用中间工作区，但不能改变左侧文件夹的长期组织方式。

### 3.3 报告视图

选中一个候选人–JD 子项后，右侧或详情工作区展示：

- 进入面试 / 不进入面试；
- 加权总分和计算明细；
- 每项核心任务的 0–4 能力等级；
- 直接证据、可迁移证据和背景证据；
- 关联理由与迁移边界；
- 证据置信度；
- 评分总审纠错记录；
- 能力缺口；
- 进入面试者的针对性面试重点；
- 实际运行节点、模型和降级记录。

不进入面试者同样展示完整报告，不生成无意义的“待确认”。

## 4. 能力评估子界面

能力评估不是旧简历评估的换名，而是后续要重新定义的候选人级工作流。

### 4.1 能力评估的对象

能力评估回答候选人自身的能力结构和边界，例如：

- 能够稳定完成哪些类型的问题；
- 能力证据来自哪些项目、论文或工作经历；
- 能力在哪些场景可迁移；
- 当前证据的强弱和缺口是什么。

它不直接输出“是否进入某个岗位面试”，也不拥有 JD 的任务权重。

### 4.2 过渡期行为

在能力评估 Agent 和评分语义正式确定前：

- 子界面可以展示“能力评估正在重构”的明确状态；
- 不得把旧通用维度、旧 Track 评分伪装成新能力评估；
- 可以展示候选人结构化简历和已确认事实，不能制造一个没有新规则支撑的总分；
- 旧 `/resume-evaluate` 路由只承担迁移兼容，不继续增加旧功能。

### 4.3 与面试准入的关联

能力评估和面试准入共享原始材料和证据基础，但准入报告必须回到 JD 核心任务进行判断：

- 能力评估可以为准入提供候选人级背景上下文；
- 准入评分不能只引用一个能力总分绕过 JD 任务证据；
- 准入节点发现的新证据可以回写候选人能力证据池，但必须保留来源和关联理由；
- 用户可以从准入报告跳转到能力评估，也可以从能力评估反查该能力被哪些 JD 任务验证过。

## 5. 共同的数据边界

两种子界面共享候选人和材料，但报告仍按不同主键保存。

### 5.1 候选人级数据

包括：

- 姓名、方向、阶段和人才档案；
- 原始简历文件和完整脱敏文本；
- 结构化教育、经历、项目、论文和技能；
- HR 补充信息；
- 论文核验和外部事实；
- 能力评估结果及其证据（未来）。

### 5.2 候选人–JD 级数据

包括：

- 当前 JD 和岗位评估卡引用；
- 核心任务评分；
- 证据、关联理由和迁移边界；
- 评分总审纠错；
- 面试准入结论；
- 面试重点；
- 运行轨迹、模型使用和降级信息。

同一个候选人可以在不同 JD 下得到不同结论。系统不生成跨 JD 总分、最佳 JD 或排他分配。

### 5.3 姓名与报告关联

报告接口必须直接返回候选人姓名和 JD 标题，前端不允许依赖当前候选人队列通过 ID 二次拼接。

候选人移出评估列表只改变列表可见性，不应让已有报告退化为 `candidate_xxx`。如果候选人被物理删除，则必须按数据级联规则明确处理关联报告，不能静默显示残缺卡片。

## 6. JD 池与岗位评估卡

### 6.1 JD 池

- JD 没有“激活 / 未激活”状态。
- JD 只在启动批次时被显式选择。
- 归档 JD 不出现在默认选择列表，但不自动删除已有报告。
- JD 的编辑、补充要求和岗位卡生成受运行中的输入锁保护。

### 6.2 岗位评估卡

岗位评估卡由 JD 原文和累计的岗位补充要求生成，无需人工确认即可用于评估。它固定：

- 岗位核心任务；
- 每项任务的描述和评价重点；
- 首要、主要、补充三档重要性；
- 0–4 等级的任务化锚点；
- 允许使用的直接、可迁移和背景证据边界。

通常 3–5 项，最多 6 项。工具名、数字、学历和实习时长不能被写成脱离实际任务的硬门槛。

岗位卡重新生成成功后，该 JD 的当前准入报告全部失效；失败时原卡、原补充要求和原报告保持不变。

## 7. 面试准入评分规则

### 7.1 能力等级

核心任务使用统一的 0–4 能力等级：

| 等级 | 含义 |
| ---: | --- |
| 0 | 没有可支撑该任务的证据 |
| 1 | 有相邻基础或背景，但没有实际完成类似任务 |
| 2 | 实际参与过相关工作，有行动或产出 |
| 3 | 能独立完成高度相似的任务并形成闭环 |
| 4 | 在复杂或多个场景中成熟完成并承担端到端责任 |

岗位卡的任务化锚点只是把这套尺度翻译到具体岗位，不形成第二套评分体系。

### 7.2 证据

每个评分必须有可追溯证据：

- 直接证据：相同或高度相似的实际任务；
- 可迁移证据：问题结构、方法或责任可迁移的相邻经历；
- 背景证据：学历、专业、技能关键词或方向兴趣，只能帮助理解。

所有推理节点都可以读取完整脱敏简历和结构化简历。证据映射不是有损输入漏斗；技能栏未写某个工具，不等于候选人不会使用该工具。

证据置信度固定为高、中、低三档，仅用于展示，不参与总分。

### 7.3 准入决策

模型不直接生成最终百分制。代码按岗位卡任务权重换算：

```text
单项百分制 = 能力等级 / 4 × 100
总分 = Σ(单项百分制 × 任务系数) / Σ任务系数
```

进入面试必须同时满足：

1. 所有首要任务等级不低于 2；
2. 加权总分不低于 50。

结论只有“进入面试”和“不进入面试”。技术失败、取消或证据纠错失败是运行状态，不是业务结论。

## 8. 运行、重评与并发

### 8.1 全用户重评

不再保留“允许强制重评”设置，也不区分管理员和普通用户。任何用户都可以对已有当前报告发起重评。

- 重评成功后原子替换当前报告和运行轨迹；
- 模型失败、超时或取消时保留旧的有效报告；
- 不向用户展示历史报告版本链；
- 失效、失败和缺少报告的配对同样可以重新运行。

### 8.2 候选人–JD 互斥锁

同一候选人–JD 配对在任何时刻只能有一个活动运行：

- 锁由后端数据库持有，不能只依赖前端禁用按钮；
- 新建批次时原子获取所有配对锁；
- 任一配对冲突时拒绝该批次，返回明确的占用信息；
- 运行完成、失败或取消后释放锁；
- 所有用户通过活动运行接口实时看到占用状态；
- 前端显示锁图标和运行状态，不能误导用户重复点击。

输入锁与配对锁是两种不同约束：前者保护简历、JD 和岗位卡不被修改，后者保护同一候选人–JD 不被并发重评。

### 8.3 LLM 并发与模型路由

所有 LLM 请求共享全局并发上限 50。批量候选人与核心任务的并行不能相乘绕过限制；
工作流自身仍可按业务需要设置更小的并行度。

文本、结构化、评估、学术核验与视觉 OCR 统一使用支持多模态的 GLM-5.3-Flash；
对话 Agent 也使用同一模型，不再在 GLM-5.3 与 GLM-5.2 之间切换：

- `OPENAI_MODEL`：对话主模型，默认 `glm-5.3-flash`；
- `OPENAI_MODEL_NON_CONVERSATION`：非对话节点模型，默认 `glm-5.3-flash`；
- Flash 请求强制启用 thinking；非对话节点默认 `reasoning_effort=low` 以保证时效，
  对话 Agent 默认 `reasoning_effort=max` 并保留完整思考内容；
- 每个节点继续记录实际模型、时间与错误信息；
- 429 / 1302 只按显式配置的兼容备用模型处理，默认不回退到旧模型。

## 9. 工作流与前端运行图

面试准入工作流保持自上而下的轻度知识图谱感：

```text
准备输入
  ↓
能力证据映射
  ↓
核心任务评分组
  ↓
证据校验与局部修正
  ↓
评分总审
  ↓
准入决策与报告
```

约束：

- 节点按真实事件从上到下生长，不允许拖拽；
- 连线只表示真实依赖；
- 节点显示业务名称、状态、一句摘要和实际模型；
- 展开节点可查看证据、推理摘要、纠错审计和错误；
- 不展示原始 chain-of-thought、完整 prompt 或密钥；
- 运行结束后，持久化工作流与当前报告一起保留；
- 对话型工作流的节点链只在当前轮运行时展示，结束后消失。

## 10. 失效、取消与输入保护

### 10.1 失效

以下变化会让受影响的当前准入报告失效：

- 候选人简历或 HR 补充信息变化；
- 对应 JD 的岗位评估卡重新生成；
- 评分规则或准入公式变化。

只记录有效 / 失效，不向用户暴露版本号或历史评分链。无关候选人和无关 JD 不受影响。

### 10.2 取消

用户可以停止单个配对或整批评估：

- 未发出的调用停止；
- 在途结果返回后丢弃；
- 本轮中间产物作废；
- 不生成半成品报告；
- 释放配对锁和输入锁。

### 10.3 输入保护

运行期间后端禁止修改本轮使用的简历、JD、岗位补充要求和岗位评估卡。无关对象仍可编辑。前端禁用只是提示，后端校验才是最终约束。

## 11. 实施顺序

本方案按以下顺序落地，先稳定产品边界，再重建能力评估：

1. 建立统一“人才评估”页面外壳和两个子界面路由。
2. 将候选人列表改为文件夹式组织，JD 评估作为候选人子项。
3. 将导入简历卡迁移到左侧候选人卡片底部，并保持运行持久化。
4. 让报告接口直接返回候选人姓名和 JD 标题，修复移出队列后的编号回退。
5. 将现有面试准入浏览、批量选择和运行图接入统一外壳。
6. 隐藏旧简历评估结果的产品入口，保留数据兼容，不再扩展旧评分链。
7. 单独定义能力评估的对象、能力维度、证据契约和评分规则。
8. 实现能力评估子界面，再接入与面试准入之间的证据反查和互跳。
9. 完成姓名关联、刷新恢复、锁竞争、取消、限流降级和英文界面回归测试后再部署。

## 12. 明确不做的事情

- 不恢复全局激活 JD 机制。
- 不把候选人做成跨 JD 的单一进面结论。
- 不把旧简历评估总分改名成能力评估总分。
- 不把学历、专业、实习时长或到岗条件变成能力硬门槛。
- 不增加 `hold` 或“待确认”业务状态。
- 不保留面向用户的历史报告版本链。
- 不让前端单独承担并发锁、输入锁或重评权限。
- 不用关键词缺失替代对项目、论文和真实工作内容的推理。

本文之后，任何页面设计和 Agent workflow 改动都应先回答两个问题：

1. 这是候选人级能力评估，还是候选人–JD 级面试准入？
2. 它是否保留了可追溯证据，并与另一个子界面建立清晰关联？

如果无法回答这两个问题，不应直接加入统一人才评估页面。
