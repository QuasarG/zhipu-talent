# 过程复盘

## 评估维度设计思路

本工具把「高潜 AI 人才」拆成 **12 个维度**，分为两组：

### 潜力维度（核心，权重 70%）

1. **学习与成长潜力**（10%）
2. **研究探索能力**（12%）
3. **工程实践能力**（12%）
4. **AI 工具 / Agent 使用能力**（10%）
5. **问题定义与独立思考**（10%）
6. **项目 Ownership**（8%）
7. **长期培养价值**（8%）

### 履历维度（辅助，权重 30%）

8. **教育背景信号**（8%）
9. **学术产出信号**（8%）
10. **项目 / 实习丰富度**（7%）
11. **成果影响力 / 可见度**（4%）
12. **方向匹配度**（3%）

选择这套维度，是因为任务目标不是传统招聘里的「谁学校更亮、论文更多」，而是判断候选人是否可能成长为 AGI 时代的研究者、工程师或技术 leader。但「学校、GPA、论文、项目丰富度」并非毫无价值——它们能提供基础信号，降低信息不对称；因此我们保留这些履历维度，但以较低权重进入总分，避免它们喧宾夺主。

真正决定高分的是 Evidence：候选人能否定义问题、搭建可运行闭环、验证假设、复盘失败，并把 AI 工具变成自己的能力杠杆。每条证据会标记具体技术栈、动作动词、量化结果和 ownership 信号。证据越具体，评分越高；只有「参与项目」「了解方向」这类表述会被压低。

## 关键 Prompt / Agent 指令片段

### 1. 简历解析 Agent（支持任意文本输入）

```text
你是简历解析 Agent。只输出 JSON 对象。
从任意格式的简历文本中提取结构化字段。
文本可能是 Markdown、纯文本、JSONL 片段或 OCR 结果。
```

这一步让系统不再强依赖 JSONL / Markdown，可以直接丢入原始文本，由 LLM 先提取结构，再进入深评 pipeline。

### 2. 深度证据挖掘 Agent

```text
你是 AI 人才潜力初评系统里的【深度证据挖掘 Agent】。
像尽调律师一样，优先提取「具体技术栈 / 具体动作动词 / 量化结果 / ownership 信号 / 验证闭环」。
每条 evidence.quote 必须尽量逐字来自简历原文，禁止扩写、脑补、编造数据。
```

这一步解决「凭空判断」和「项目真实性难辨」的问题。模型被要求从原文中抽取实体和动作，并把信号拆成结构化字段。

### 3. 跨领域对齐打分 Agent

```text
你是 AI 人才潜力初评系统里的【跨领域对齐打分 Agent】。
每个维度 1-5 分，weighted_score = score × weight × 20。
潜力维度必须基于具体 evidence 判断，不能只看背景。
履历维度低权重参考，不要给满分。
不要给所有维度相同分数，要根据 evidence 区分强弱。
```

这一步让 CV、NLP、Agent、AI4Science 等不同方向的候选人在同一套 Rubric 下可比，同时拉开区分度。

### 4. 逻辑判官与防幻觉节点

```text
你是 AI 人才潜力初评系统里的【逻辑判官与防幻觉节点】。
检查规则：
1. 评分理由引用的 evidence id 必须存在。
2. 潜力维度 score >= 4.5 必须有具体技术栈 / 动作动词 / 量化结果 / ownership 中的两项以上。
3. 评分理由不能主要依赖学校、GPA、排名、名企光环。
4. 所有维度不能都集中在同一个分数。
5. evidence <= 1 但 score >= 4.0 必须给 critic_flags。
```

Critic 节点承担核心兜底职责，必要时把状态打回 Scorer 重新打分一次。

## 踩坑与处理

### 1. 完全盲化背景导致信息损失

最初把学校、GPA、排名完全盲化，失去了履历辅助信号。现在改为「保留原始教育文本，但仅以低权重进入履历维度评分」，既削弱背景偏见，又不浪费信息。

### 2. 批量导入过于复杂

最初设计了两个 LLM agent（初评 + 回顾确认），增加了调用次数和失败点。现在合并为单一轻量 Import Agent，只提取列表展示所需的基本信息和分类，不再进入深评 pipeline。

### 3. LLM 输出格式不稳定

所有 LLM 调用都使用 `response_format={"type": "json_object"}`，并用 Pydantic 模型做后验校验。针对 LLM 常见的字段类型错误（risk_notes 给字符串、critic_flags 给 dict、overall_score 给浮点、level 和 tier 写反等），每个节点都做了 normalize 兜底。

### 4. 评分安全分问题

早期 LLM 倾向于给所有候选人相近分数。新版 Scorer Prompt 明确要求「不要给所有维度相同分数」，并加入 Critic 的「防安全分」规则，强制拉开区分度。

## 当前局限

- 只支持文本简历（JSONL / Markdown / TXT），暂未处理 PDF 版式。
- 论文、GitHub 链接、实验结果和开源贡献没有联网核验，只能生成「待验证点」。
- 需要配置 DeepSeek / OpenAI-compatible API key 才能运行完整评估。
- LLM 推理成本和延迟随简历数量线性增长；顺序处理适合 SSE 推流，但 10 份简历仍需要数分钟。
- 评分本质仍是模型对简历文本的语义推断，无法判断项目真实贡献比例、导师指导程度、论文是否最终被接收等事实。

## 再给两天会做什么

1. **接入真实模型跑样例并校准 Rubric**：用少量简历人工标注，调整维度权重和 Prompt 里的强弱信号示例。
2. **支持 PDF 解析**：把版式质量、LaTeX 使用、结构清晰度作为弱信号加入评估。
3. **SSE 推流评估组件**：把顺序处理过程实时推送到前端，用户能看到每个节点进度。
4. **增加外部核验入口**：对论文、GitHub、项目链接做可选联网检查。
5. **引入人工复核界面**：让 HR 能修改证据权重、标记误判、保存反馈，形成下一轮校准数据。
