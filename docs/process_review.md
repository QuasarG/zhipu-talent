# AI 人才潜力初评助手：过程复盘

## 我如何理解“AGI 时代值得培养的人”

这个任务最容易做成一个传统简历排序器：学校更亮、论文更多、指标更漂亮的人排在前面，剩下的人被压到后面。但我理解这里真正要找的并不是“当前履历最光鲜的人”，而是未来可能在 AGI 时代持续长出来的人。这样的候选人未必已经拥有最完整的论文列表，也未必每一项指标都能在简历里写得很漂亮；更重要的是，他是否能把一个模糊问题拆开，找到可验证的路径，用工程和 AI 工具放大自己的迭代速度，并且在失败、约束和不确定性里继续推进。

因此，我把“潜力”拆成了两层。第一层是核心潜力：学习与成长、研究探索、工程实践、AI 工具 / Agent 使用、问题定义、项目 ownership 和长期培养价值。第二层是辅助履历信号：教育背景、学术产出、项目丰富度、成果影响力和方向匹配。辅助信号不是无效信息，它可以降低不确定性；但它不能直接替代对“人”的判断。一个候选人来自强背景、写过漂亮论文题目，只说明他曾经进入过一个不错的训练场，不等于他已经具备独立定义问题和完成闭环的能力。

在实际评分里，我更看重简历中能否出现几类硬证据：具体技术栈、具体动作动词、可验证指标、失败归因、baseline 或 ablation、本人负责范围，以及 AI 工具或自动化系统是否真的改变了他的工作方式。比如“负责 benchmark 设计、模型评测和错误归因”比“参与多模态研究”更有价值；“用 Triton 实现 kernel 并在 128K 上下文降低显存”比“熟悉高效推理”更有价值；“设计构图-出题-求解-验证-反思的多智能体闭环”比“研究 Agentic Data Generation”更有价值。这个判断标准背后其实只有一个原则：我希望系统尽量看见候选人真实做事的肌肉，而不是被简历包装的光泽晃到。

## 系统如何落地这个判断

当前 Demo 是一个可运行的 LangGraph 多节点评估链路。前端支持导入候选人、查看人才库、触发单人或批量评估，并展示每个节点进度。后端把一次评估拆成五步：先由 Normalizer 把学校、GPA、排名等高偏置信号折叠成低权重档位；再由 Evidence Extractor 像尽调一样从简历里抽取证据；随后 Scorer 按 rubric 打分；Critic 负责检查幻觉、主观高分和安全分；最后 Formatter 生成面谈可用的画像、风险和追问。

这个拆分的意义是把“事实抽取”和“主观判断”分开。LLM 很擅长读文本和归纳，但它也容易顺着漂亮表述给高分，所以我不让打分节点直接读简历后自由发挥，而是要求它基于结构化 evidence 评分。每条 evidence 都带有 dimension、quote、signals、strength、has_metric、has_specific_tool、has_ownership 等字段。这样后续如果某个维度被打高，至少能追问：它到底靠哪条证据支撑？这条证据是不是原文中真的存在？它只是论文标题，还是包含了方法、动作和验证闭环？

目前 rubric 采用 12 个维度，总分 100。核心潜力维度合计 88%，辅助履历维度合计 12%。其中工程实践、问题定义、AI 工具 / Agent 使用和 ownership 权重较高，因为它们更接近“能否在不确定环境里持续产出”的能力。教育背景只有 2%，学术产出 3.5%，方向匹配 2%，这些信号被保留但被压低，目的是避免系统重新滑回传统履历崇拜。

评分本身采用 1-5 分，再乘以维度权重。5 分要求同时看到具体技术、本人动作、量化或可验证结果、闭环验证，并且能体现独立定义或推进；4 分表示证据较强但还需要面谈确认贡献边界；3 分通常是有项目事实和技术词，但缺少指标、闭环或 ownership；2 分更多是方向词、论文题目或背景信号；1 分则说明几乎没有证据。为了减少模型“端水”，代码里还加了硬性封顶规则：没有证据的维度最高 1.5；AI Agent 维度如果没有 Agent、RAG、工具调用、自动验证、路由或工作流证据，最高 2.0；ownership 没有本人动作最高 3.0；problem definition 没有痛点、约束、baseline 或评价指标最高 3.2。

## 关键 Prompt 与 AI 协作方式

第一个关键 Prompt 是背景标准化。我的目标不是完全脱敏，而是屏蔽具体细节、降低相关权重，用分级信号替代具体学校、GPA 和排名。这个节点会把教育背景折叠成 school_tier、gpa_tier、rank_tier、degree_tier 和 academic_signal_tier。这样后续模型仍然知道“训练背景大致强弱”，但不能直接拿具体学校名或精确成绩给高分。

第二个关键 Prompt 是证据挖掘。我要求模型“像尽调律师一样”优先找具体技术栈、动作动词、量化结果、ownership 和验证闭环。这个 Prompt 的作用不是让模型总结简历，而是逼它从文本里挖出可以被质询的事实。后续我又放宽了 quote 校验：最初系统要求证据引文必须逐字出现在原文，结果把语义重组但可追溯的证据误判成幻觉。现在的做法是检查关键术语、数字、技术栈和动作是否能从原简历追溯；如果真的不可追溯，Critic 会优先让证据节点回炉重抽，而不是直接把“幻觉风险”展示给前端。

第三个关键 Prompt 是跨领域评分。我明确告诉模型，这不是传统履历排序，也不是按论文名气或学校背景给分，而是用本批候选人的对比样本校准“什么是真正高潜”。比如有些候选人方向很时髦，但缺少 baseline、指标定义和本人贡献边界；有些候选人项目看起来不够华丽，但工程闭环、验证路径和问题拆解非常硬。Prompt 中反复强调这些区别，是为了让模型别把“简历漂亮”误当成“值得培养”。

第四个关键 Prompt 是 Critic。它负责检查 evidence id 是否存在、评分理由是否引用了不存在事实、高分维度是否有足够硬证据、是否过度依赖学校或论文、是否所有维度都给安全分。如果问题会影响分层，它会要求回炉。这里的设计初衷是：AI 不是只负责给答案，也要负责质疑自己的答案。

## 当前样例结果与人工复核观察

基于当前样例输出，系统大体能把明显缺少闭环证据的候选人放到较低层级，也能识别出多模态几何数据合成、Coding Agent、长上下文工程优化等方向里更有闭环潜力的人。但人工复核时我发现一个重要问题：候选人 06 被系统性低估了。

候选人 06 的方向是低精度训练、量化感知训练、FP8/FP4、大模型训练稳定性和软硬协同优化。他的简历里有“负责 FP8 训练稳定性验证”“分析 Transformer 激活值 outlier 对量化误差和训练崩溃的影响”“提出通道重参数化与归一化前移的结构改造”“设计激活优先的量化校准策略”等内容。它不像 Agent 应用型候选人那样天然拥有“工具调用、任务规划、自动验证、多智能体闭环”这些关键词，但它触及的是大模型训练和推理效率的底层约束。如果未来 AGI 系统需要更长上下文、更低成本、更高吞吐和更稳定的训练基础设施，这类人才的战略价值不应该被简单低估。

这个坑说明 V1 的评价体系有过拟合“AI Native Application”的倾向。我们把“AI 工具 / Agent 使用能力”“问题定义闭环”“应用层验证”放得很重，这是合理的，因为任务初衷是识别 AGI 时代能借助 AI 放大自己的高潜候选人；但这也会让底层系统型人才吃亏。系统型人才的闭环不是“做一个 Agent workflow”，而是“把一个训练或推理系统瓶颈拆成数值稳定性、硬件约束、kernel、精度格式、吞吐、显存和收敛风险，并通过实验把它压下去”。这类证据如果仍用应用型模板来衡量，就会显得不够“AI Native”，但它可能恰恰是 AGI 基础设施所需要的稀缺能力。

因此，V1 的结论不能被理解为最终人才裁决，而应该理解为一个偏应用型高潜筛选器。候选人 06 是一个很好的反例：它提醒我们，AGI 人才不只有“会用 Agent 做产品和数据闭环”的人，也包括“能让模型训练、推理和系统栈继续向前推进”的人。这个发现比单个分数更重要。

## V2.0 迭代计划：双轨评价体系

如果继续优化，我会把当前单一 rubric 拆成双轨体系：AI Native Application Track 和 AGI Infra & System Track。两条轨道共享底层原则：都要看真实贡献、问题定义、验证闭环和长期成长性；但它们承认不同类型人才的证据形态不同。

AI Native Application Track 继续关注 Agent、RAG、工具调用、自动评测、数据闭环、人机协作和产品化实验。这个轨道适合候选人 02、03、07、08 这类方向。它的高分证据包括：能把任务拆成感知、规划、执行、验证；能设计多智能体或工具链闭环；能用自动化评测和错误归因持续提升系统；能把 AI 从“调用模型”变成工作流里的生产力杠杆。

AGI Infra & System Track 则应该单独评价模型系统、训练稳定性、推理优化、低精度、并行训练、kernel、数据引擎、评测基础设施和底层平台能力。这个轨道适合候选人 01、06 这类方向，也可能覆盖部分长上下文、训练框架和高性能推理人才。它的高分证据不一定是 Agent 使用，而是是否能定位系统瓶颈，是否理解软硬件约束，是否能在精度、吞吐、显存、稳定性和收敛之间做取舍，是否能设计可复现实验并把优化落到真实系统。

双轨之后，总分不应该只给一个“统一潜力分”。更合理的输出是：候选人主轨道、辅轨道、轨道内排名、跨轨解释和推荐培养路径。比如候选人 06 在 AI Native Application Track 可能不是顶尖，但在 AGI Infra & System Track 应该被重新评估为强候选；候选人 02 在 Application Track 非常强，但未必应该和 FP8 训练稳定性人才用同一个 Agent 权重硬比。这样既能保留横向比较，又不会把不同类型的潜力压成同一种形状。

## 一致性测试设计

LLM 评估还有一个必须面对的问题：同一个候选人多次独立评估，分数和排序是否稳定？如果系统每次都能产出流畅理由，但分数大幅波动，那么它就更像一个会写评语的随机数生成器，而不是可靠的初筛助手。

为此我新增了 `scripts/run_consistency_eval.py`，并实际完成了 10 位候选人各 5 次的独立完整评估。每次评估都会重新跑 Normalizer、Evidence Extractor、Scorer、Critic 和 Formatter；每轮内按综合分排序；最后统计每位候选人的均分、分数标准差、最高最低差、平均名次、名次波动、等级分布和分层分布。脚本采用断点续跑和单候选人重试，不写数据库，避免网络抖动导致整组实验作废。

完整 5 轮结果显示，当前系统的排序并不是完全随机，但波动和偏差都值得警惕。按平均名次看，前三位是候选人02均分84、平均名次1、候选人07均分72.8、平均名次2.6、候选人03均分69.6、平均名次3.2。其中候选人02的应用型 Agent / 数据闭环特征非常符合 V1 rubric，因此稳定处在高位；候选人07和候选人08也受益于 Agent、自动化评测或系统闭环信号。相对地，候选人06的均分为 57.6，平均名次 6.6，分数范围 9，名次范围 1。这个结果进一步印证了前面提到的坑：底层基建型人才虽然可能具有很强的长期战略价值，但在偏 AI Native Application 的 V1 评价体系里仍然容易被压到中段。

实验过程中也暴露了工程层面的稳定性风险。真实 API 链路会出现握手超时或响应超时，LLM 偶尔仍会输出越界字段，例如 evidence strength 给出 0，被 Pydantic 拦截后需要重试；这说明 JSON 模式不等于完全可靠，后验校验、断点续跑和中间落盘仍然必要。从统计上看，分数波动最大的候选人是候选人03，分数标准差 4.96，分数范围 15；名次波动最大的候选人是候选人03，名次范围 3。这些候选人应该进入人工复核，而不是只看单次分数。

V2.0 我会把一致性测试纳入校准流程：如果某候选人的分数标准差过大，系统不应该只给一个分数，而应该提示“模型判断不稳定，需要人工复核”；如果排名在多次运行中剧烈变化，说明 rubric 或 prompt 对该类型候选人的证据解释不够稳。最终进入前端的也不应该只有单次分数，而可以展示均分、置信区间和稳定性标记。

## 踩过的坑：单次 LLM 评分不应被当成稳定结论

一致性实验让我确认了一个比“打分有点波动”更严肃的问题：V1 版本如果只保留单次评估结果，容易把模型的一次性解释误当成稳定判断。候选人03在 5 次评估中的分数范围达到 15 分，名次范围达到 3；候选人02虽然始终排第一，但等级在 S 和 A 之间切换；候选人06则在 B/C 边界附近波动，并且 5 次里有 4 次进入暂缓。这说明当前系统的排序有一定方向性，但单次分数的置信度不足，尤其是对证据形态不完全贴合 rubric 的候选人，模型会在“应该给机会”和“证据不够硬”之间摇摆。

这个坑的根源有三层。第一，LLM 对同一份简历的证据抽取并不完全一致，不同轮次可能抽到不同 evidence，从而影响后续打分。第二，当前 Scorer 虽然有硬性封顶，但仍有一部分判断依赖模型对“证据强弱”的语义解释；当候选人处在边界区间时，少量解释差异就会放大成分数差异。第三，V1 用单一 rubric 评价不同类型候选人，导致应用型 Agent 证据更容易被稳定识别，而底层系统型、跨域型或论文型证据更容易出现不稳定判断。

对应的改进方式不应该只是“再调一调 prompt”。下一版应该把一致性作为系统输出的一部分：每位候选人至少进行多次轻量复评，前端展示均分、标准差、最高最低区间和名次波动；当分数标准差或名次范围超过阈值时，自动标记为“需人工复核”，而不是直接按单次分数入库。证据抽取也应该做稳定化：多轮 evidence 先合并去重，再由 Scorer 基于稳定证据集评分，减少某一轮漏抽证据带来的波动。最后，双轨 rubric 需要和一致性测试一起上线：如果一个候选人在 Application Track 低分但在 Infra Track 可能高潜，系统应该输出“轨道不确定 / 建议换轨复评”，而不是把他压成一个看似精确的低分。

## 当前局限与兜底

当前系统已经能跑通从导入、评估到前端展示的闭环，也能把证据链、评分理由和面谈追问串起来。但它仍然只是一个初筛助手，不是最终判断器。

第一，项目真实性无法仅靠简历文本完全验证。论文是否真实存在、实验指标是否可复现、GitHub 贡献是否主要由候选人完成，这些都需要外部材料或面谈追问。系统现在的做法是把这些不确定性显式写进风险与追问，而不是假装已经验证。

第二，模型仍可能受到表述风格影响。会写简历的人更容易提供完整证据，不会写的人可能被低估。这是所有文本简历筛选都会遇到的问题，因此后续最好要求候选人补充论文 PDF、项目链接、代码贡献、实验报告或技术说明。

第三，当前体系虽然降低了学校、GPA 和论文名气权重，但仍然需要人工校准“什么证据算强”。尤其是 06 暴露出的底层基建人才低估问题，说明 rubric 必须随目标人才画像迭代。一个好的评估系统不应该假装自己一开始就懂所有人才类型，而应该能记录误判、解释误判，并把误判转成下一版规则。

第四，LLM 输出稳定性需要长期测试。JSON 约束、Pydantic 校验、Critic 回炉和证据可追溯检查能减少格式错误和幻觉，但不能天然保证多次独立评估完全一致。稳定性统计、人工 gold set、双轨 rubric 和分数置信区间，是下一步真正让系统可靠起来的关键。

## 如果再给两天

我会优先做四件事。第一，把双轨评价体系落成代码：导入后先判断候选人的主轨道，再用对应 rubric 打分，同时保留跨轨解释。第二，完成 10x5 一致性实验，并把分数标准差、排名波动和不稳定候选人直接展示在前端。第三，建立一个小型人工校准集，把 02、06、07、01 这类不同画像的候选人作为标尺，持续调整 prompt 和硬性封顶规则。第四，增加外部核验入口，让论文、GitHub、项目链接和实验报告可以被人工或工具进一步验证。

这个项目最有价值的地方，不是它已经给出了一个完美排序，而是它把“我为什么看好一个人”拆成了可讨论、可追问、可迭代的证据链。AGI 人才判断本来就不该是一张静态打分表，而应该是一个持续校准的判断系统。
