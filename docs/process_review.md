# 过程复盘

## 评估维度设计思路

本工具把「高潜 AI 人才」拆成 7 个维度：学习与成长潜力、研究探索能力、工程实践能力、AI 工具 / Agent 使用能力、问题定义与独立思考、项目 ownership、长期培养价值。

选择这些维度，是因为任务目标不是传统招聘里的「谁学校更亮、论文更多」，而是判断候选人是否可能成长为 AGI 时代的研究者、工程师或技术 leader。学校、GPA、会议名只作为背景信息；真正有用的是候选人能否定义问题、搭建可运行闭环、验证假设、复盘失败，并把 AI 工具变成自己的能力杠杆。

打分方式采用「统一 Rubric + LLM 语义判断」。不同方向不直接比较「谁的 mAP 更高」或「谁的论文更像顶会」，而是把 Evidence List 放进同一套维度中由模型评分。每条证据会标记具体工具、动作动词、量化结果和 ownership 信号。证据越具体，评分越高；只有「参与项目」「了解方向」这类表述会被压低。

## 关键 Prompt / Agent 指令片段

### 1. 深度证据挖掘 Agent

```text
你是 AI 人才潜力初评系统里的【深度证据挖掘 Agent】。
只输出 JSON 对象，顶层字段必须是 evidence。

任务：
1. 从脱敏简历中抽取能支撑人才潜力判断的证据。
2. 每条 evidence.quote 必须逐字来自 raw_text 或项目/成果/技能字段，禁止改写、扩写、脑补。
3. 不要因为学校、GPA、排名给证据加分；这些背景已被脱敏。
4. 优先抽取具体动作、技术栈、量化结果、ownership、验证闭环。
```

这一步解决「凭空判断」和「项目真实性难辨」的问题。模型被要求像尽调律师一样，只抽取原文中能找到的实体和动作，并把信号拆成结构化字段，为后续打分提供可引用的事实底座。

### 2. 跨领域对齐打分 Agent

```text
你是 AI 人才潜力初评系统里的【跨领域对齐打分 Agent】。
只输出 JSON 对象，字段必须是 overall_score, level, tier, dimension_scores。

评分目标：
识别长期培养价值，不是传统履历排序。不要直接按学校、GPA、论文名气给高分。
只允许根据 evidence 列表打分，不允许使用 evidence 之外的信息编造理由。
```

这一步让 CV、NLP、Agent、AI4Science 等不同方向的候选人在同一套 Rubric 下可比。模型不被允许引用简历外的信息，也不被允许比较不可比的单项指标，只能从 Evidence List 中推断各维度表现。

### 3. 逻辑判官与防幻觉节点

```text
你是 AI 人才潜力初评系统里的【逻辑判官与防幻觉节点】。
只输出 JSON 对象，字段必须是 critic_flags, needs_rescore。

检查规则：
1. 防幻觉：评分理由和证据引用必须能在 evidence 中找到，不得引用不存在的事实。
2. 防主观：如果某维度给到 4.5+，但 evidence 中缺少具体技术栈、量化结果、本人动作或验证闭环，必须给 critic_flags。
3. 防背景偏见：如果理由依赖学校、GPA、排名、名企而不是项目证据，必须给 critic_flags。
4. 如果问题会影响综合评分，needs_rescore=true；如果只是小的表述问题，needs_rescore=false。
```

Critic 节点承担核心兜底职责。它不只检查格式，还检查评分逻辑是否被证据支撑，并在必要时把状态打回 Scorer 重新打分一次。

## 踩坑与处理

### 1. 过度依赖背景信号

Normalizer 会把学校、排名、GPA 盲化成粗粒度占位，Scorer 的 Prompt 明确要求不直接读取原始教育背景。盲化后的教育信息仅用于 HR 风险提示，不进入潜力评分。

### 2. 证据和判断混在一起

模型层把 `EvidenceItem` 和 `DimensionScore` 分开。Formatter 只能基于 Evidence 生成优势、风险和追问，不能脱离证据写评价。这样即使 LLM 想「发挥」，也会被结构约束拉回来。

### 3. Mock 测试中的 Prompt 子串冲突

在单元测试里，「回顾确认 Agent」的 Prompt 包含「复核初评分类 Agent 的分类结果」这句话，导致 mock 先匹配到「初评分类 Agent」分支、返回了错误格式。修复方式是把「回顾确认 Agent」的判断条件放在「初评分类 Agent」之前，并增加回归测试覆盖批量导入全流程。

### 4. LLM 输出格式不稳定

所有 LLM 调用都使用 `response_format={"type": "json_object"}`，并用 Pydantic 模型做后验校验。如果模型返回的 JSON 字段缺失或类型错误，会立刻抛异常而不是把脏数据往下传。关键节点（证据引用完整性）还加了硬规则兜底。

## 当前局限

- 只支持 JSONL / Markdown 文本简历，暂未处理 PDF 版式。真实投递以 PDF 为主，版式本身也可能是信号，但当前 MVP 先做通文字闭环。
- 论文、GitHub 链接、实验结果和开源贡献没有联网核验，只能生成「待验证点」，不能替代人工背调。
- 需要配置 DeepSeek / OpenAI-compatible API key 才能运行完整评估。离线 demo 依赖已有的 `outputs/talent_evaluations.json` 样例。
- LLM 推理成本和延迟会随简历数量线性增长，10 份简历的批量评估需要多次 API 调用。
- 评分本质仍是模型对简历文本的语义推断，无法判断项目真实贡献比例、导师指导程度、论文是否最终被接收等事实。

## 再给两天会做什么

1. **接入真实模型跑一轮样例并校准 Rubric**：用少量简历人工标注，观察 LLM 打分与专家判断的偏差，调整维度权重和 Prompt 里的强弱信号示例。
2. **支持 PDF 解析**：把版式质量、LaTeX 使用、结构清晰度作为弱信号加入评估。
3. **增加外部核验入口**：对论文、GitHub、项目链接做可选的联网检查，并把核验状态作为风险提示。
4. **引入人工复核界面**：让 HR 能修改证据权重、标记误判、保存反馈，形成下一轮校准数据。
5. **优化成本和延迟**：对证据抽取和打分做缓存，避免重复调用；探索一次请求处理多个候选人的批量模式。
